## 2. Accessibility fixes

- **No skip link on any auth route.** `apps/web/components/auth-shell.tsx` has no equivalent of the `(app)` shell's `<a className="skip-link" href="#main-content">` (confirmed present at `apps/web/app/(app)/layout.tsx:23-25`). Add the same pattern to `AuthShell`, pointing at a new `id="main-content"` on its `<main className="auth-shell-card-wrap">`.
- **Duplicate `<h1>` on every auth page.** `AuthShell`'s marketing tagline (`auth-shell.tsx:79`, e.g. "Verify the evidence before approving the content.") renders as an `<h1>` inside the `<aside>`, and `AuthForm`'s real per-mode heading (`auth-form.tsx:308`, `<h1 id="auth-title">`) renders inside `<main>` — two H1s per page. The tagline is marketing copy, not a page heading; change it to a `<p>` (matching the surrounding `<p className="auth-shell-eyebrow">`/`<p>` siblings' semantic level). `AuthForm`'s heading remains the page's one real H1.
- **No route uses Next.js's `loading.tsx` convention anywhere** (confirmed via `Glob apps/web/**/loading.tsx` → zero matches across all ~13 routes). Two ad-hoc client-side "Loading…" states exist (`dashboard-listings-client.tsx`, `catalog-control-center.tsx`) but most routes have no loading affordance at all. Add a `loading.tsx` to every route: `dashboard`, `catalog`, `queue`, `batches`, `batches/[id]`, `listings/new`, `listings/import`, `listings/[id]`, `admin`, `jobs`, `quality`, `system-map`, and one shared `loading.tsx` for the `(auth)` route group. All reuse one small, shared skeleton/spinner component rather than 13 bespoke ones.
- **`AuthForm`'s password hint and inline errors aren't `aria-describedby`-associated with their inputs** (confirmed: the password input at `auth-form.tsx:342-355` has no `aria-describedby`; its `<small>Use 12 to 128 characters.</small>` hint has no `id` at all — pure visual proximity, no programmatic link). Add an `id` to the hint and reference it via `aria-describedby` on the password and confirm-password inputs.
- **`listing-queue.tsx`'s disabled checkbox label doesn't distinguish rows.** When a checkbox is disabled (the listing isn't yet approvable), its label is `` `${item.openBlockingFlagCount} 個未解決的合規標記` `` (`listing-queue.tsx:83`) — two rows with the same flag count get identical labels, so a screen-reader user can't tell them apart. Prepend `item.title`, matching the enabled-state label's own pattern (`` `選取 ${item.title}` ``, line 80-83).
- **`catalog-control-center.tsx`'s `<table>` has no accessible name of its own** (only inherits one from the ancestor `<section aria-label="商品控制中心">`, one level removed). Add `aria-label` directly on the `<table>` element.
- **Two real touch-target failures**, found via direct WCAG contrast/sizing computation, not assumed-passing: `.queue-action` is `min-height: 42px` (`globals.css:654`), below the 44px minimum, and overrides `.secondary-button`'s correct 46px due to cascade order; `.locale-toggle button` (`globals.css:204-210`) has no `min-height` at all. Fix both to `min-height: 44px`.

## 3. Security fix — XLSX total decompressed-size bound

`packages/shopline/src/bulk-form-xlsx.ts` already bounds each zip entry's decompressed size via zlib's native `maxOutputLength` option (`MAX_INFLATED_BYTES = 64 * 1024 * 1024`, confirmed present and real — not a post-hoc check, zlib itself aborts inflation past this). What's missing: a bound on the _sum_ across all entries in the archive combined — `readZipEntries` decompresses every central-directory entry unconditionally, so a many-small-entries archive (each under the 64MB per-entry cap) isn't bounded by any total-size check, only by the implicit 65,535-entry-count ceiling and whatever the upload's own size limit is upstream. Add `MAX_TOTAL_INFLATED_BYTES = 96 * 1024 * 1024` (1.5× the per-entry cap — generous for a legitimate multi-sheet/multi-part workbook, while still bounding a pathological many-entry archive; the real Opak workbook this system targets is 182KB compressed, several orders of magnitude under this), tracked as a running total during `readZipEntries`, throwing the same `BulkFormWorkbookError` the per-entry check already uses.

## 4. Correlation IDs

**Revised after implementation-grounding research** (verified directly against `jobs-ledger.ts`'s 4 source-type mappings and their real audit-write call sites): the "no migration, join by id" mechanism only holds for 2 of the 4 lifecycle stages `/jobs` surfaces. `EnrichmentBatch` and `ExportAttempt` audit events are written with `entityId = the row's own id` (`enrichment-batch-service.ts`'s `enrichment_batch.created`/`.advanced`, and the export route's `listing.bulk_export_created`) — genuinely joinable today, no migration. `PublishJob` and `PipelineRunSummary`, however, are audited with `entityId = the listing's id` (`apps/worker/src/publish-product.ts`, `apps/worker/src/listing-pipeline.ts`), and one listing can have multiple rows of each — there is no id-based way to pick out which specific row a given audit event belongs to. Making that side correlatable would need a new column on both tables plus threading the id through `packages/jobs`' queue-message contract into `apps/worker` — a cross-app change meaningfully larger than this package's other items, and explicitly deferred (§7).

**Scope for this package:** thread one correlation ID through the import → batch → export lifecycle only, where `auditEvents.metadata` (already a schema-less `jsonb` column, no migration) already supports it. Generate the ID at the point a batch or import begins, stamp it into `metadata.correlationId` on `listing.imported` / `listing.import_refreshed` → `enrichment_batch.created` / `enrichment_batch.advanced` → `listing.bulk_export_created` / `listing.bulk_form_exported` / `listing.csv_exported`. Surface it as a new column in `/jobs`' ledger view for the `batch` and `export` lane kinds only (`apps/web/lib/jobs-ledger.ts`'s `LedgerEntry` type gains an optional `correlationId: string | null`; the `publish_job`/`pipeline_run` lanes always report `null`, which is accurate, not a bug, given the scope above).

## 5. Metrics

Also derived from `audit_events` — no new table, but **revised after research**: two of the four metrics need a new audit _write_, not just a new query, since the underlying per-row data doesn't exist in the audit table today.

- **Retry counts** — `listing.publish_failed` already exists with `{versionId, errorCode}` metadata (confirmed real, unchanged from the original design). A new aggregate query is sufficient; no new write needed.
- **Version conflicts** — confirmed genuinely unaudited today (the 409 in `apps/web/app/api/listings/[id]/approve/route.ts` throws directly, no `audit.write` call anywhere in that path). Add a new `listing.review_conflict` audit write at that rejection site, as the original design already anticipated.
- **Stale-source rejections** — also confirmed genuinely unaudited: `assertApprovalFreshness`/`assertExportFreshness` (`packages/core/src/content-freshness.ts` and callers) are pure functions with no `AuditWriter` parameter at all; their rejection is never written anywhere. Add a new audit write (reusing the same `listing.review_conflict` action with a `reason` field distinguishing `"stale_source"` from `"version_mismatch"`, or a second dedicated action — decide in the plan) at the freshness-gate rejection call sites in both the approve route and `bulk-export-service.ts`.
- **Partial-import counts** — the original design's assumption that `listing.imported`'s metadata already carries `refreshedProducts`/`issueCount` was wrong: that data exists only in a `console.info` log line (`apps/web/app/api/listings/import/route.ts:162-171`, `event: "listing.bulk_form_imported"`), never in the audit table. Add one new aggregate-level audit write at that same call site, mirroring the log's real fields (`parsedRows`/`createdDrafts`/`refreshedProducts`/`issues.length`), so the metric becomes queryable rather than log-only.

A new aggregate method on `packages/db/src/repositories/audit.ts` (currently write-only — confirmed no `count`/`aggregate`/`query` method exists) counts these action/reason combinations within a time window. Surfaced as new tiles on `/jobs` (matching its existing per-lane count-badge pattern) rather than a new dashboard.

## 6. Testing

- Accessibility: a jsdom/happy-dom test per fix confirming the specific DOM property (skip link href, single `<h1>` per rendered auth page, `aria-describedby` pointing at a real element, disabled-checkbox label containing the item title, table `aria-label` present) — matching this session's established DOM-testing conventions, not a new tool.
- Touch targets: a CSS-level test isn't practical the same way (no computed-style assertion tooling in this test suite) — verify by reading the rule directly (`min-height: 44px` present) plus a manual browser check at both breakpoints, matching how earlier packages this session verified CSS fixes.
- XLSX bound: a new test constructing a synthetic multi-entry archive whose total decompressed size exceeds 96MB but where every individual entry stays under 64MB, asserting `BulkFormWorkbookError` is thrown — proving the _total_ bound is real and distinct from the existing per-entry one.
- Correlation IDs: an integration test asserting the same `correlationId` appears in an import event's metadata and its resulting batch-creation event's metadata, plus a test asserting `jobs-ledger.ts` correctly reports `null` (not a crash or a wrong value) for `publish_job`/`pipeline_run` lane entries, documenting the deferred scope rather than leaving it an untested assumption.
- Metrics: unit tests for the new aggregate query against a fixture with a known mix of event types, asserting exact counts per metric; a test confirming the new `listing.review_conflict` and aggregate-import audit writes actually fire at their respective rejection/import call sites, not just that the query works once data exists.

## 7. Explicitly out of scope

- **Correlation IDs for `publish_jobs`/`pipeline_runs`** (the SHOPLINE-delivery side of a listing's lifecycle) — would need a new migration on both tables plus threading the id through `packages/jobs`' queue-message contract into `apps/worker`, a cross-app change meaningfully larger than this package's other items (§4). Named as its own follow-up, not a silent gap.
- The pre-existing, dev-mode-only 500 on `/api/auth/register`'s local `next dev` module resolution — confirmed unrelated to any package's actual code (untouched by the H/I merge), confirmed absent from `next build` (what CI/Vercel actually run) — already flagged as its own separate follow-up task, not part of this package.
- A dedicated "stale-version conflict" UI on the review page — the existing generic `role="alert"` error handling already surfaces a 409 correctly (confirmed via direct code read); a bespoke "someone else edited this, reload?" affordance would be a UX enhancement, not an accessibility or security gap, and isn't called for by any confirmed audit finding.
- Any change to Better Auth configuration (already resolved via documentation in Package C, not reopened here).
- Any of the items already confirmed done in the audit: contrast ratios (all 5 real token pairings pass WCAG AA), keyboard focus-trap/restoration in the mobile drawer (already implemented and tested), icon-only action naming (no icons exist anywhere in this codebase), log redaction in Packages D–I's own logging (clean), cross-workspace RLS test coverage for every table that currently exists (enrichment batches, confirmation ledger, platform products, export attempts — all confirmed to have real isolation tests), and `listing-fields-form.tsx`'s existing field-metadata `aria-describedby` association (already correct).
