# Wukong E-commerce OS repository audit

Audit date: 2026-10-25, America/New_York. Repository: `YNWAforever/wukong-ecommerce-os`.
Baseline: `9c2aa25fedb35453c61d1f3018d5d2fd37eda15a` (`main`, also the clean initial local HEAD).

No current source-level P0 was verified. The audit identified **7 P1 and 8 P2 findings**. This PR records the audit and acceptance criteria; it does **not** claim to fix product code. The implementation authorization was limited to safe P0 cleanup, so P1/P2 work remains explicitly queued. Product scope, provider settings and production resources are unchanged.

The highest engineering priorities are vulnerable native image decoding, login CSRF, dependency patches, destructive-test isolation, inaccurate migration inventory, dropped runtime flags, and Workerd-incompatible provider requests. Prior production reports describe more severe operational risks; their current status is unknown and is tracked separately below.

## Concrete evidence and proposed regression checks

### Login CSRF and logging

F02 does not require an existing victim session. A `text/plain` top-level form can produce a strict-schema JSON body with `callbackURL` equal to `=`; the callback sanitizer correctly falls back, but the password handler still forwards successful session cookies. Better Auth's own first-login Fetch Metadata protection sees the synthesized headerless server request instead of the browser's origin. The local Request/JSON parsing reproduction succeeded; an authenticated browser exploit was not run. Fix at the external boundary and test both malicious form rejection and legitimate same-origin JSON login. A library upgrade alone does not repair the wrapper.

For F08, installed Better Auth's get-session catch logs the full adapter error; installed Drizzle formats failed bound queries with parameters. This establishes a potential token-to-log path, not observed credential leakage. A synthetic error canary and a sanitized logger are the appropriate regression test.

### Worker redirect incompatibility

The installed Workerd runtime rejects `new Request("https://example.invalid", {redirect: "error"})` with its explicit unsupported-mode TypeError. This was reproduced using `workerd test` without sockets or external calls. The production binding passes Workerd's fetch to Photoroom; TypeSafe uses the same runtime fetch. Existing Node/injected-fetch tests miss the runtime restriction. A patch must use `manual`, reject 3xx, and prove that no credentials follow a redirect. Preserve Photoroom ambiguous-outcome handling and TypeSafe's non-blocking advisory policy.

### Data and recovery safety

F04 is operator-misconfiguration risk, not an unauthenticated database attack. Existing test labels and localhost defaults are insufficient to establish a disposable target. Some rehearsal guards check the URL pathname but permit query parameters; installed postgres.js can use query settings to override startup database/user options. Validate before test-module import/client construction, including effective fallback variables and enabled optional rehearsal URL families. Run no destructive suite until target identity is established.

For F05, a function-name check cannot distinguish `0002`'s old enrollment body from `0047`'s membership insertion, or `0000`'s one-argument membership function from `0048`'s overload and workspace-list function. Add independent omission tests. The CLI also exits zero when only the reported role/grants are false (`packages/db/src/cli/schema-inventory.ts:33`); retain the runbook's manual grant checks until that exit policy is tightened. This supporting gap is lower priority than the false migration markers.
